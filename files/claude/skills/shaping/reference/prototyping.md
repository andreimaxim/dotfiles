# Prototyping

Use code to answer a learning question, not to make a favored architecture appear inevitable.
Make the question, representative path, discriminating evidence, firm constraints, and deliberate
omissions clear before editing. A shaping-only request does not authorize code changes; obtain
permission for the experiment when it is outside the requested activity.

Build the smallest vertical path that can answer the question in the real system. Use production
names and boundaries so feedback is meaningful. Controlled substitutes are fine only when they do
not hide the uncertainty being tested.

Treat the prototype as evolutionary code that may remain, with provisional design—not a promise of
production readiness. Preserve security, integrity, and compatibility constraints. Avoid expanding
into the full feature, general hardening, or speculative abstractions.

Verify the discriminating behavior, inspect the resulting friction, and explain what the evidence
supports or rules out, what remains omitted or uncertain, and how it changes the shape. Link the code
needed to judge it. Remove throwaway experiments, but do not discard intentional evolutionary code.
Completion means the learning question is answered or its blocker is exposed, not that the feature
is built. Further implementation and shared-state actions require their own authorization.
